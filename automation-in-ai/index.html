Core Concepts | Rule-Based

Rule-based automation

Rule-based automation uses deterministic logic. If a condition is met, an action fires. It is reliable, auditable, and fast, but brittle when inputs vary or rules conflict.

  • Best for: high-volume, stable-logic tasks (payment routing, threshold alerts).
  • Weakness: cannot handle ambiguity or novel inputs.
  • Governance: rule changes require version control and approval workflows.
Core Concepts | AI-Assisted

AI-assisted automation

AI-assisted automation uses machine learning or language models to generate recommendations, classifications, or drafts. A human remains in the loop for final decisions.

  • Best for: tasks with unstructured inputs (document review, email triage).
  • Weakness: model confidence varies; requires calibration and monitoring.
  • Governance: output review, confidence thresholds, and audit logging.
Core Concepts | Autonomous

Fully autonomous automation

Autonomous automation operates without human review in the decision loop. It is appropriate only when the cost of errors is low, reversibility is built in, or speed requirements make human review impractical.

  • Best for: real-time fraud scoring, automated reconciliation matching.
  • Weakness: errors propagate silently if monitoring is insufficient.
  • Governance: circuit breakers, anomaly alerts, and regular model audits.

Core Concepts | Workflow Anatomy

Anatomy of a bankable workflow

  1. Trigger: What starts the process? (Customer request, scheduled batch, event signal.)
  2. Input: What data or documents enter the workflow?
  3. Steps: What transformations, checks, or decisions occur?
  4. Exception: What happens when a step fails or produces ambiguous output?
  5. Output: What is delivered, to whom, and in what format?
  6. Feedback: How does the process learn from outcomes?
Core Concepts | Mapping Notation

Workflow mapping: practical notation

You do not need formal BPMN for this module. Use a simple notation with clear conventions.

  • Rectangle: A process step (action or transformation).
  • Diamond: A decision point (yes/no or branching logic).
  • Oval: Start or end of the workflow.
  • Arrow: Direction of flow, labelled with conditions where applicable.
  • Dashed box: An exception or fallback path.

Core Concepts | AI Assistants

AI assistants and chatbots in banking

AI assistants handle customer-facing interactions: answering questions, routing requests, and collecting information. Chatbot design in banking requires strict guardrails.

  • Scope limitation: the assistant must know what it cannot answer.
  • Escalation paths: when should the bot hand off to a human agent?
  • Data sensitivity: the bot must never expose account details without authentication.
  • Tone and compliance: responses must align with regulatory and brand standards.
Core Concepts | Chatbot Design

Designing a governed chatbot

Intent recognition

Classify what the customer wants. Use confidence thresholds to route low-confidence intents to human agents.

Response generation

Use approved templates for regulated topics. Allow AI-generated responses only for informational queries.

Escalation logic

Define triggers: failed authentication, complaint keywords, repeated misunderstanding, or customer request.

Core Concepts | API Integration

API integration patterns

Automation in banking often requires connecting systems through APIs. Common patterns include:

  • Request-response: Synchronous calls for real-time data (credit checks, balance inquiries).
  • Event-driven: Asynchronous processing triggered by system events (new account, transaction alert).
  • Batch processing: Scheduled bulk operations (end-of-day reconciliation, report generation).
  • Webhook: External systems push updates to your workflow (payment gateway notifications).

Core Concepts | Common Failures

Common automation failures

Over-automation

Automating steps that require judgment. The system makes decisions nobody reviewed, and errors compound silently.

Missing exceptions

Designing only the happy path. When unexpected inputs arrive, the workflow stalls or produces wrong outputs.

Ungoverned rollout

Deploying automation without metrics, monitoring, or rollback plans. Problems surface only after damage is done.

Core Concepts | Human-in-the-Loop

Human-in-the-loop design

Human-in-the-loop (HITL) is not a single pattern. It is a design decision about where, when, and how humans interact with automated processes.

  • Pre-action review: Human approves before the system acts (loan approvals, large transactions).
  • Post-action audit: System acts, human reviews a sample afterward (transaction monitoring).
  • Exception handling: Human intervenes only when the system cannot proceed (edge cases, low confidence).
  • Override capability: Human can reverse or modify an automated decision at any time.
Core Concepts | Governance

Governance and monitoring

Automation without governance is a liability. Every automated workflow needs:

  1. An owner accountable for the workflow's performance and compliance.
  2. Monitoring dashboards tracking throughput, error rates, and exception volumes.
  3. Alerting rules that trigger investigation when metrics breach thresholds.
  4. Scheduled reviews to assess whether automation assumptions still hold.
  5. Change management processes for updating rules, models, or thresholds.

Guided Walkthrough | KYC Overview

Walkthrough 1: KYC document review

Know Your Customer (KYC) document review is a core compliance process. Analysts verify identity documents, check sanctions lists, and assess risk profiles. The current process at AJB handles approximately 200 cases per week with an average turnaround of 48 hours.

Guided Walkthrough | KYC Steps

KYC review: current workflow steps

  1. Customer submits identity documents through the portal.
  2. Operations team logs the submission and assigns it to an analyst.
  3. Analyst opens each document and checks for completeness.
  4. Analyst extracts key fields (name, ID number, date of birth, address).
  5. System runs a sanctions and PEP (Politically Exposed Person) check.
  6. Analyst compares extracted data against application form entries.
  7. Analyst writes a risk assessment summary.
  8. Senior analyst reviews and approves or rejects the case.
  9. System sends the outcome notification to the customer.

Guided Walkthrough | KYC Exception Paths

KYC review: exception paths

  • Incomplete documents: System flags missing items and sends a request back to the customer. Workflow pauses until resubmission.
  • Sanctions match: Immediate escalation to compliance team. Workflow halts. No automated progression allowed.
  • Low OCR confidence: Field extraction falls below 85% confidence. Route to manual extraction by analyst.
  • Data mismatch: Extracted fields do not match application data. Flag for analyst review with highlighted discrepancies.
  • System downtime: If the sanctions API is unavailable, queue the case and alert operations. Do not skip the check.
Guided Walkthrough | KYC Design

KYC review: automation design summary

Automate

Queue assignment (round-robin by workload). Completeness check (document classifier). Field extraction (OCR with confidence scoring). Data comparison (rule-based matching). Notification (template-based email).

Keep manual

Risk summary (AI drafts, analyst reviews). Senior approval (human judgment required). Sanctions escalation (compliance team only). Any case below confidence thresholds.

Guided Walkthrough | Reconciliation Overview

Walkthrough 2: daily transaction reconciliation

Every day, AJB reconciles transactions between its core banking system, payment gateway, and card processor. The team manually investigates mismatches. Current volume: approximately 15,000 transactions per day with a 2.3% mismatch rate.

Guided Walkthrough | Reconciliation Steps

Reconciliation: current workflow

  1. Extract transaction records from core banking, payment gateway, and card processor.
  2. Load records into a reconciliation spreadsheet.
  3. Match transactions by reference number, amount, and date.
  4. Flag unmatched records as exceptions.
  5. Analyst investigates each exception manually.
  6. Analyst classifies the exception (timing difference, duplicate, genuine error).
  7. Analyst resolves or escalates the exception.
  8. Supervisor reviews and signs off on the daily reconciliation report.
Guided Walkthrough | Reconciliation Automation

Reconciliation: automation opportunities

High potential

Data extraction (automated feeds). Record matching (deterministic logic). Timing-difference classification (rule-based: auto-resolve if matched within T+1). Report generation (templated output).

Requires judgment

Genuine error investigation (context-dependent). Duplicate detection in ambiguous cases (fuzzy matching + analyst review). Escalation decisions (materiality thresholds). Final sign-off (supervisor accountability).

Guided Walkthrough | Reconciliation Exceptions

Reconciliation: exception design

  • Data feed failure: If any source system feed is missing or incomplete, halt reconciliation and alert operations. Do not run partial matching.
  • Spike in mismatch rate: If daily mismatch rate exceeds 5%, trigger a manual review of the matching logic before auto-resolving any cases.
  • Large-value mismatch: Any mismatch above SAR 50,000 requires immediate manual investigation regardless of category.
  • Duplicate transaction: Flag both records and prevent auto-resolution. Analyst must confirm which record is correct.

Guided Walkthrough | Integration Points

Integration architecture for reconciliation

Automated reconciliation requires reliable data pipelines between systems. Design considerations:

  • Data extraction: scheduled API pulls or file drops from each source system.
  • Data normalization: standardize formats (date, currency, reference) before matching.
  • Matching engine: deterministic first (exact match), then fuzzy match for near-matches.
  • Results storage: write matched and unmatched records to a reconciliation database with full audit trail.
  • Alerting: push notifications to operations team for exceptions that require action.
Guided Walkthrough | Design Principles

Automation design principles

  1. Start narrow: Automate one step well before expanding.
  2. Fail safe: When in doubt, route to a human. Never fail silently.
  3. Monitor everything: If you cannot measure it, do not automate it.
  4. Design for rollback: Every automation must be reversible within a defined time window.
  5. Document assumptions: State what must be true for the automation to work correctly.
  6. Review regularly: Automation that was correct last quarter may not be correct today.

Case Critique | Introduction

Case discussion and critique

Now we examine real-world automation decisions, including ones that went wrong. Critical thinking about failures teaches more than celebrating successes.

Case Critique | Case 1

Case 1: the over-automated loan processor

A regional bank automated 90% of its personal loan decisions, including edge cases that previously required human judgment. Within three months, approval rates for high-risk applicants increased by 35%. The bank discovered the issue only after delinquency rates spiked in the following quarter.

What governance gap allowed this to happen? What monitoring would have caught it earlier?
Case Critique | Case 1 Analysis

Case 1: analysis framework

  • Root cause: No separate monitoring of approval rates by risk segment. Aggregate metrics looked normal.
  • Missing control: Segment-level alerting on approval rate changes. Threshold: flag if any risk segment shifts by more than 10%.
  • Design fix: High-risk applications should require human review regardless of model confidence.
  • Lesson: Aggregate metrics hide distribution shifts. Monitor at the segment level.
Case Critique | Case 2

Case 2: the chatbot that could not say "I don't know"

A bank deployed a customer-facing chatbot for account inquiries. The bot was designed to always provide an answer. When asked questions outside its training scope, it generated plausible but incorrect responses about account features, interest rates, and fee structures. Customer complaints doubled in six weeks.

What design decision created this failure? How would you fix it?
Case Critique | Case 2 Analysis

Case 2: analysis framework

  • Root cause: No confidence threshold or scope boundary. The bot was optimized for response rate, not accuracy.
  • Missing control: Intent confidence scoring with a minimum threshold. Below-threshold queries route to human agents.
  • Design fix: Implement a "scope fence." If the query does not match a known intent with at least 75% confidence, respond with "Let me connect you with an agent who can help."
  • Lesson: An AI system that cannot say "I don't know" is dangerous in a regulated environment.
Case Critique | Case 3

Case 3: reconciliation without rollback

A bank automated daily reconciliation with auto-resolution for timing differences. A software update changed the timestamp format in one source system. The matching engine silently misclassified thousands of genuine mismatches as timing differences and auto-resolved them. The issue was discovered five days later during a manual audit.

What assumption broke? What circuit breaker was missing?
Case Critique | Case 3 Analysis

Case 3: analysis framework

  • Root cause: The automation assumed stable input formats. No validation check on incoming data structure.
  • Missing control: Input schema validation before matching begins. Format change detection triggers a halt and alert.
  • Missing circuit breaker: Alert if auto-resolution rate exceeds historical average by more than 20%.
  • Design fix: Add data quality gates at the input stage. Validate schema, format, and completeness before processing.
  • Lesson: Automation that does not validate its inputs inherits every upstream error silently.
Case Critique | Synthesis

Patterns across failures

Monitoring gaps

All three cases lacked segment-level or threshold-based monitoring. Aggregate dashboards hid the problem.

Missing boundaries

No system knew when to stop. No confidence thresholds, no scope fences, no format validators.

Delayed detection

Problems were discovered days or weeks later. Real-time alerting on anomalies would have cut exposure dramatically.

Recap | Common Pitfalls

Pitfalls to avoid after this module

  • Do not automate a decision before you can explain its exception path.
  • Do not measure only throughput. Measure quality, error rate, and customer impact.
  • Do not skip the pilot. "It works in testing" is not evidence of production readiness.
  • Do not treat AI confidence scores as certainty. Calibrate and validate regularly.
  • Do not remove human review to save time. Remove it only when evidence supports doing so.
